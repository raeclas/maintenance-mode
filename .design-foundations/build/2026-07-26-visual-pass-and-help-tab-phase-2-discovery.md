## Design Decisions

**1. Help is a real seventh tab, gated by nothing (always open), not a
`?`-triggered pane.** Per the plan's own Assumption — the user chose this
explicitly over a modal. The existing `#helpBtn` (`?`) becomes a shortcut
that switches to the Help tab rather than opening `#helpModal`, which is
retired; its one piece of content (the Ban Wave judgement + bot-DPS-fraction
paragraph) relocates into Help's Training section rather than disappearing.

**2. Help's sections are gated by the SAME unlock condition as their tab.**
The plan's own edge case states it directly: "A locked tab's unlock
condition is state, not teaching — it stays." If Help showed full Dungeon
mechanics to a player who hasn't unlocked Training yet, it would spoil
content the existing progressive-unlock IA (REMAKE-DESIGN.md's arc
reasoning, cited in `## IA`'s Validation note) deliberately withholds. So a
locked tab's Help section collapses to the same milestone-only string
already shipped on that tab's nav-button `title` (`Unlocks at 100 Combat
Power.`, etc.) — reusing an existing string rather than inventing a second
"locked" register. Boss's Help section is never locked, matching Boss's own
always-open state.

**3. Tab-row re-fit: `repeat(4,1fr)`, 4+3, not a naive extension of
`repeat(3,1fr)`.** Journey doctrine's Hick's law citation (Hick–Hyman 1952,
already used elsewhere in this document for the six-tab row) still applies
at seven — grouping/staging isn't required at this count, Miller/Cowan's
~4±1 governs *memory* load not *visible item* count (the doc's own standing
citation). What changes is the grid math: `repeat(3,1fr)` with 7 children
auto-wraps 3+3+1, leaving the last row two-thirds empty around one orphaned
button. Rendered and measured (see DW-2.4 evidence): neither variant
literally overflows at 375px, but the plan's constraint text says "the row
must be re-fitted, not merely extended," and 3+3+1 is the extension the
sentence is written against. `repeat(4,1fr)` (4+3) is the re-fit: uniform
button width (87px, well above the 44px touch minimum), no orphan, same
carpentry (`--radius-control`, the v3 button gloss/bevel) reused unchanged —
this is a grid-track count change only, zero new colour, zero new
typography, staying inside this phase's OUT-of-scope boundary on visual
styling.

**4. Relocated copy is moved, not rewritten, wherever the original sentence
survives context-free.** The plan's own constraint ("Relocation, not
deletion") and several rows' own history (the crit line and farm-interval
line were already trimmed by Phase 1 with an explicit "moves to Help in
Phase 2" note) point the same way: reuse the already-approved words. Where a
sentence assumed it was sitting beside a specific rendered number (e.g. "same
as ATK" as a non-repeat instruction, or a POINTER phrased for its live
position), it's lightly restitched for a standalone reference context — noted
per-row in the relocation table where this happens.

**5. What "moves" vs "stays," stated as one rule (doctrine-cited).** Applying
the plan's own line ("A live surface keeps any string a player needs AT the
moment of the decision; everything that teaches a mechanic in general
moves") together with content-design's citations: Redish (*Letting Go of the
Words*, 2007) — the reader scans for their current goal, not a general
lesson, so a repeatable "how X works" rule that doesn't depend on current
state moves; Yifrah's condition+fix formula and the existing destructive-
confirm pattern (Ban Wave's armed-state message, already correct) are
exactly the class of string that stays, because they state a consequence at
the moment of the action, not a general mechanic. Concretely: every `h3` sub
/ named "teaching line" element in the six tabs' Explained-once registers
moves (16 blocks total, plus the 2 already-cut Boss items and the retired
help-modal content = 19 relocations); every per-row cost/chance/state
readout, every error condition+fix message, every destructive-confirm
message, and every POINTER stays untouched. Full table in JOURNEY.md.
